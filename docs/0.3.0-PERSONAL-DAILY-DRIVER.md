# BlazaresSpaces 0.3.0 — Personal Daily Driver

## Terminology and native Spaces decision

This milestone calls the app-managed contexts **Virtual Spaces**. “macOS
Spaces” or “Native Spaces” refers only to Mission Control. Virtual Spaces keep
the existing logical parking/restoration semantics and do not claim to create,
select, delete, or synchronize native Spaces. The public-API feasibility
assessment and the selected MODE B architecture are documented in
[NATIVE-SPACES-FEASIBILITY.md](NATIVE-SPACES-FEASIBILITY.md).

## Goal

0.3.0 is the first milestone intended for real daily use by the project owner on a multi-display Mac. It is not a new architecture experiment. The 0.2.0 domain, application-service, persistence, matching, recovery, and safety boundaries remain authoritative.

The acceptance question is simple:

> Can BlazaresSpaces be started in the morning and used throughout a normal workday as the primary logical-desktop controller without disturbing unmanaged work?

## Product invariant

**ONE VIRTUAL SPACE = ONE COMPLETE WINDOW CONTEXT ACROSS ALL CONNECTED DISPLAYS.**

A Virtual Space is global, not per-display. Managed windows may belong to one Virtual Space, several Virtual Spaces, or all Virtual Spaces through sticky semantics. BlazaresSpaces does not tile or choose the user's layout; it preserves user-created contexts.

## Safety boundary

Daily-driver status does not weaken authorization.

- Discovery remains read-only.
- Discovery never implies management authorization.
- Newly discovered windows remain unmanaged until an explicit user action enrolls them.
- Unmanaged windows are never switching, parking, restoration, or recovery targets.
- `NEVER MANAGE` remains authoritative and includes the conservative Citrix exclusion policy.
- Fullscreen and minimized windows remain conservative/unsupported when mutation cannot be guaranteed safe.
- Ambiguous persisted-window matches are never guessed.
- Accessibility loss or unsafe display-topology changes degrade/pause mutation instead of guessing.
- Recovery only targets windows managed/parked by BlazaresSpaces.

## 0.3.0 priorities

### 1. Daily-driver UI

The primary window should present Virtual Space management first. Inspector, AX diagnostics, raw display information, capture labs, and experimental diagnostics should become secondary/advanced surfaces rather than dominating the normal workflow.

The normal path should be obvious:

1. See the active Virtual Space.
2. Create/rename/reorder Virtual Spaces.
3. Explicitly manage a safe window.
4. Move it to, add it to, or show it on all Virtual Spaces.
5. Switch desktops by UI or keyboard.
6. Stop managing a window safely.
7. Recover managed windows when necessary.

### 2. Explicit management UX

Every discovered eligible window should clearly distinguish `Unmanaged`, `Managed`, `Sticky`, and `NEVER MANAGE` states. Enrollment must be an explicit action. Assignment actions must preserve the existing semantics:

- **Move to Virtual Space** replaces normal memberships with the target.
- **Show/Add on Virtual Space** adds membership without removing other memberships.
- **Show on All Virtual Spaces** sets sticky semantics.
- **Stop Managing** first recovers a parked window when necessary, then removes BlazaresSpaces control without closing the application/window.

A managed window must never accidentally end with an invalid zero-membership state.

### 3. Switching ergonomics

Global keyboard switching is a first-class daily workflow. Virtual-Space-by-index and next/previous switching must use the serialized application switching path and must never bypass safety checks. Rapid requests must not produce overlapping AX pipelines.

The active desktop must be immediately visible in the main UI and menu-bar controller. Shortcut conflicts/failures should be reported without destabilizing workspace state.

### 4. Persistence and startup

0.3.0 uses the versioned persistence system as the authoritative state. Virtual Space names, positional `workspaceOrder`, active selection, memberships, sticky state, preferences, shortcuts, and privacy-safe durable descriptors are encoded in `PersistedStateV1`. Runtime AX identities and temporary parking state are not persisted. Migration validates that positional order contains every persisted workspace exactly once; invalid state is rejected rather than applied.

Startup remains conservative: loading configuration and discovering a likely runtime window do not authorize physical mutation. High-confidence restoration still requires the defined review/confirmation policy; ambiguous matches remain unresolved.

### 5. Multi-display dogfooding

The primary validation topology is multiple displays, including three-display use. Validate windows distributed across displays, shared windows, sticky windows, negative display coordinates, and repeated A → B → C → A switching.

A display connection/disconnection/rearrangement must not cause blind restoration to stale coordinates. If the topology cannot be handled safely, switching degrades and recovery remains available.

### 6. Recovery and failure visibility

Recovery must remain prominent but not frightening. A user must be able to understand whether BlazaresSpaces is `idle`, `switching`, `recovering`, or `degraded`, and why.

Partial failure of one managed window must not abort safe operations for unrelated managed windows. Reports must avoid sensitive titles by default.

### 7. Dogfooding feedback

0.3.0 should favor observable, diagnosable behavior over clever automation. Real-use failures should be captured as reproducible issues/tests before adding broader automation. Do not add automatic arbitrary-window rules merely to reduce clicks during this milestone.

## Architecture rules

`docs/ARCHITECTURE.md` remains authoritative. 0.3.0 must not move orchestration back into SwiftUI or `DiagnosticsViewModel`. New daily-driver UI sends intent through the application layer. Domain rules remain independently testable. Concrete AX, display, hotkey, and persistence implementations remain infrastructure/adapters.

If implementation reveals that the architecture document is stale, update the document with the actual checked-in architecture rather than documenting aspirational behavior as implemented.

## Required automated coverage

Preserve all previous tests and add coverage where missing for:

- explicit manage/unmanage lifecycle;
- Move vs Add membership semantics;
- sticky enable/disable;
- shared windows receiving no unnecessary mutation;
- empty desktops and zero managed windows;
- rapid/serialized switching;
- A → B → C → A planning;
- missing runtime windows and partial failures;
- recovery targeting managed/parked windows only;
- `NEVER MANAGE` exclusion;
- Accessibility loss;
- topology invalidation;
- persistence round-trip of daily-driver configuration;
- conservative restoration ambiguity.

UI tests must remain non-destructive and must not select arbitrary real external windows.

## Manual daily-driver gate

Before calling 0.3.0 ready for daily use, perform a real-Mac validation with disposable/safe windows:

- Launch and refresh: no external window moves.
- Create at least Work, Development, University, and Personal desktops.
- Rename and reorder them.
- Explicitly manage disposable windows across multiple displays.
- Put A only on Work, B only on Development, C on Work + Development, and D on all desktops.
- Switch Work → Development → University → Personal via UI and keyboard.
- Verify C remains visible when shared and receives no unnecessary AX movement.
- Verify D remains visible everywhere.
- Repeat switching with windows distributed across three displays.
- Rapidly request several desktop switches and verify geometry remains coherent.
- Verify unmanaged work remains untouched.
- Verify Citrix is `NEVER MANAGE` and untouched.
- Stop managing a window and verify it remains open and visible.
- Exercise Recover Managed Windows.
- Quit cleanly after switching and verify BlazaresSpaces does not intentionally strand managed windows parked off-screen.
- Relaunch and verify persisted logical configuration returns without automatic external-window mutation.
- If safe, test display disconnect/reconnect and Accessibility permission loss/recovery.

Any failure that can strand or mutate unmanaged work blocks daily-driver readiness.

## Focused-window actions

The menu bar can inspect the currently focused external window and offer explicit Move/Show/Manage actions. The application re-reads focus and compares the runtime identity immediately before mutation. A changed, stale, unavailable, or excluded window is not mutated. Sticky changes preserve at least one valid membership, and `NEVER MANAGE` windows cannot be enrolled or changed by these actions.

## Out of scope for 0.3.0

Do not implement native macOS Spaces manipulation, private Mission Control/WindowServer APIs, SIP changes, tiling, automatic layouts, aggressive fuzzy matching, automatic application relaunch, z-order reconstruction, cloud sync, telemetry, Desktop Cube, Metal transitions, or elaborate animations.

## Definition of done

0.3.0 is code-complete when the normal desktop workflow is clearly separated from diagnostics, explicit management and assignment are understandable, keyboard/menu-bar switching uses the safe serialized application path, persistence/recovery remain integrated, all automated tests/builds pass, architecture boundaries remain intact, and the manual gate is documented and ready to execute.

0.3.0 is **daily-driver validated** only after the manual real-Mac gate passes. Code completion alone must not be described as proof of real-world safety.

## Acceptance status

**Code-complete / manual gate pending.** The automated suite uses pure domain/planner fakes and non-destructive UI assertions; it does not prove real macOS Accessibility writes, hotkey conflicts, crash recovery, or three-monitor hotplug behavior.

Before calling this daily-driver validated, Edward must test on the real Mac: refresh with unmanaged and Citrix windows open; create/rename/reorder Work, Development, University, and Personal; explicitly enroll disposable windows; verify Move vs Add and Sticky on/off; switch through all desktops using UI, menu bar, and shortcuts; repeat across three displays and with rapid requests; verify shared windows remain visible and unmanaged/NEVER MANAGE windows remain untouched; run Recover Managed Windows; stop managing a parked window and confirm it is recovered first; quit cleanly; and, only with a safe setup, test display topology and Accessibility loss/recovery.

Any unmanaged-window mutation, guessed restoration, stranded managed window, overlapping AX pipeline, shortcut-registration crash, or unsafe topology/permission response blocks validation. Code complete must remain distinct from real-Mac validation; unsupported fullscreen/native Spaces behavior and z-order restoration remain known limitations.
