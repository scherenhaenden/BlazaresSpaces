# 0.4.0 Native Space lifecycle evidence

This note records the concrete implementation path inspected before enabling
the direct SkyLight lifecycle bridge.

## What the reference implementation actually does

The current yabai `src/space_manager.c` does not call `CGSSpaceCreate` or
`CGSSpaceDestroy` from its application process. `space_manager_add_space`
delegates to `scripting_addition_create_space`, and
`space_manager_destroy_space` delegates to
`scripting_addition_destroy_space` (see lines 952–983 of the upstream source).
The scripting addition runs inside Dock, where the private Mission Control
operations have the required WindowServer authority. The same file documents
that native window moves use the bridged Objective-C operation when present
(`SLSBridgedMoveWindowsToManagedSpaceOperation`, lines 610–648).

The CGSInternal header independently confirms the direct symbols and ABI:

```c
CGSSpaceID CGSSpaceCreate(CGSConnectionID cid, void *null,
                          CFDictionaryRef options);
void CGSSpaceDestroy(CGSConnectionID cid, CGSSpaceID sid);
void CGSShowSpaces(CGSConnectionID cid, CFArrayRef spaces);
void CGSHideSpaces(CGSConnectionID cid, CFArrayRef spaces);
```

The supported create options are `type` and optional `uuid`; a display
identifier is not a documented option. Display association therefore cannot be
inferred from the return value. BlazaresSpaces now calls `CGSShowSpaces` after
creation and accepts the result only when a fresh
`SLSCopyManagedDisplaySpaces` snapshot finds exactly one new ordinary Space on
the requested display with the returned runtime ID.

Destruction hides the owned Space first, calls `CGSSpaceDestroy`, and accepts
success only after a fresh topology no longer contains the persisted identity.
The existing ownership, UUID, display, current-space, and last-ordinary-space
guards remain mandatory.

## Security and operating-system requirements

The direct calls are dynamically resolved from SkyLight and are not a stable
public API. On current macOS versions, yabai's create/destroy path requires its
Dock scripting addition and partially disabled SIP; this application does not
inject into Dock or silently change SIP. Consequently the direct path is
capability-gated and still rejects a result that is not attached to the target
display. A real-Mac experiment with a permitted Dock helper is required before
claiming production readiness.
